# LonghuaCRM Architecture Specification v1

> Версия: 1.0
> Статус: Draft (в разработке)

---

# 1. Назначение документа

Данный документ является главным архитектурным документом проекта LonghuaCRM.

Он описывает принципы построения системы, модель данных, архитектуру модулей и правила разработки.

Если код противоречит данному документу, правильным считается документ. Код должен быть приведён в соответствие архитектуре.

---

# 2. Цель проекта

LonghuaCRM — коммерческая CRM-платформа для управления образовательными организациями.

На первом этапе система предназначена для школы китайского языка Longhua.

Архитектура должна позволять в будущем использовать систему в других образовательных организациях без полного переписывания проекта.

---

# 3. Основные принципы

Проект строится по следующим принципам.

* Простая архитектура.
* Минимальное количество магии.
* Код должен быть понятен без комментариев.
* Один модуль отвечает только за одну область.
* Один сервис выполняет одну задачу.
* Бизнес-логика не должна находиться в контроллерах.
* PostgreSQL является единственным источником данных.
* Все изменения структуры базы данных выполняются через миграции.
* Все основные бизнес-сущности должны храниться в отдельных таблицах.
* Использование json/jsonb допускается только для динамических данных, которые невозможно заранее описать структурой таблиц.

# 6. Правила хранения данных

Каждая бизнес-сущность должна иметь собственную Entity и собственную таблицу PostgreSQL.

Не допускается объединение нескольких различных сущностей в одно jsonb-поле.

Правильный пример:

Student

Teacher

Lesson

Payment

Group

Schedule

Каждая из перечисленных сущностей должна иметь отдельную таблицу.

jsonb допускается использовать только для:

* пользовательских настроек;
* метаданных;
* временных данных;
* логов;
* Telegram Update (при необходимости хранения исходного объекта).

# 8. Telegram

Telegram работает только через Webhook.

Polling используется исключительно для локальной разработки при невозможности использовать Webhook.

Работа Telegram должна быть разделена на три уровня:

Telegram Controller

↓

Telegram Service

↓

Telegram API Client

Telegram API Client содержит исключительно работу с Telegram Bot API.

Бизнес-логика в Telegram API Client запрещена.

---

# 9. Работа с базой данных

Каждая Entity имеет собственный Repository.

Сервисы работают через Repository.

Repository отвечает только за получение и сохранение данных.

Вся бизнес-логика находится исключительно в Service.

# 11. Правила разработки

Запрещается:

* писать SQL в контроллерах;
* хранить бизнес-логику в Entity;
* использовать глобальные переменные;
* дублировать данные в нескольких таблицах;
* хранить имя преподавателя внутри Lesson;
* хранить имя ученика внутри Lesson.

Разрешается хранить только ссылки между сущностями.
