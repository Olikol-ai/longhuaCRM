# Backend Architecture v1 (после ухода от Base44)

## 1. Зафиксированное решение

- Backend: `NestJS` (один сервер)
- ORM: `TypeORM`
- DB: `PostgreSQL`
- Frontend: `React` (вне рамок этого документа)

Модель запуска v1:
- Один backend-процесс (или один контейнер backend)
- Одна PostgreSQL база
- Без Redis на старте
- Без микросервисов на старте

## 2. Границы системы

Внутри backend:
- API слой (controllers)
- Application слой (use-cases/services)
- Domain правила (валидации/политики)
- Data access слой (repositories/TypeORM)

Снаружи backend:
- React-клиент
- Telegram API
- Платёжный провайдер (Alfa Bank)

## 3. Модульная структура (в одном NestJS приложении)

- `AuthModule`
- `UsersModule`
- `SchedulingModule`
- `BillingModule`
- `MaterialsModule`
- `NotificationsModule`
- `AnalyticsModule`
- `IntegrationsModule` (адаптеры внешних API)
- `CommonModule` (ошибки, DTO, guards, утилиты)

Принцип:
- Межмодульное общение через сервисы/интерфейсы внутри приложения.
- Прямой доступ к БД только через репозитории соответствующего модуля.

## 4. Кто где работает

### 4.1 React (клиент)
- Работает в браузере.
- Делает HTTP-запросы только в backend API.
- Не ходит напрямую в PostgreSQL, Telegram, Alfa Bank.

### 4.2 NestJS backend
- Принимает API-запросы от React.
- Применяет auth, RBAC, валидации, бизнес-правила.
- Выполняет транзакции в PostgreSQL.
- Вызывает внешние интеграции через `IntegrationsModule`.

### 4.3 PostgreSQL
- Хранит бизнес-данные (users, lessons, payments, materials, access и т.д.).
- Не публикуется наружу в интернет.
- Доступна только backend-серверу.

### 4.4 Внешние сервисы
- Telegram: отправка уведомлений из backend.
- Alfa Bank: создание платежа и обработка webhook в backend.

## 5. Цепочки взаимодействия

## 5.1 Аутентификация
1. React -> `POST /auth/login` (или OAuth callback).
2. `AuthModule` проверяет данные, выдаёт access/refresh.
3. `UsersModule` подтягивает профиль/роль.
4. React использует access token для дальнейших запросов.

## 5.2 Управление пользователями и ролями
1. React (admin) -> `PATCH /users/:id/role`.
2. `UsersModule` валидирует права admin.
3. Обновляет роль в БД.
4. При необходимости синхронизирует профиль teacher/student.

## 5.3 Уроки и расписание
1. React -> `POST /lessons` или `POST /lessons/series`.
2. `SchedulingModule` валидирует конфликты/правила календаря.
3. Пишет уроки в БД.
4. При изменениях статуса (`completed/cancelled/missed`) применяет доменные правила.

## 5.4 Баланс и платежи
1. React -> `POST /payments/init`.
2. `BillingModule` создаёт запись платежа в статусе `pending`.
3. `IntegrationsModule` создаёт заказ в Alfa Bank.
4. Alfa Bank -> webhook `POST /payments/webhook/alfa`.
5. `BillingModule` валидирует подпись/идемпотентность и переводит платёж в `success/failed`.
6. Обновляет ledger баланса ученика транзакционно.

## 5.5 Уведомления
1. Доменные события (урок скоро, урок завершён, платёж успешен).
2. `NotificationsModule` строит сообщение по шаблону.
3. `IntegrationsModule` отправляет в Telegram.
4. Результат отправки логируется в БД (delivery log).

## 5.6 Материалы и доступ
1. React -> CRUD материалов/курсов.
2. `MaterialsModule` проверяет роль и policy доступа.
3. Для выдачи доступа создаёт/обновляет ACL записи.
4. При запросе учеником фильтрует материалы по ACL + бизнес-условиям.

## 6. Правила коммуникации между модулями

- `SchedulingModule` не меняет баланс напрямую в SQL:
  вызывает `BillingDomainService`/команду баланса.
- `BillingModule` единственная точка изменения баланса и платёжных статусов.
- `NotificationsModule` не содержит бизнес-решений «когда отправлять», только «как отправлять».
- `IntegrationsModule` не знает бизнес-контекст, только адаптеры API.

## 7. Транзакционные зоны (критично)

Транзакции PostgreSQL обязательны для:
- смены статуса платежа + изменение баланса;
- завершения урока + списания баланса;
- отмены урока по правилу времени + перерасчёт баланса;
- массовых операций по серии уроков.

## 8. Минимальные нефункциональные требования v1

- Все критичные команды идемпотентны (особенно webhook-платежи).
- Аудит-лог для финансовых и ролевых изменений.
- DB backup по расписанию.
- Health endpoints: `/health/live`, `/health/ready`.
- Централизованный error format.

## 9. Что откладываем после v1

- Redis и очереди (добавить при росте нагрузки/объёма уведомлений).
- Разнос на микросервисы.
- Отдельный аналитический контур (DWH/реплики).

## 10. Итог

Архитектура v1: один backend на NestJS, PostgreSQL как единое хранилище, строгая модульность и централизация критичных бизнес-операций в backend. Это даёт быстрый старт для одного разработчика и оставляет безопасный путь к масштабированию без переписывания с нуля.

## 11. Размещение PostgreSQL и связь с API (Docker)

Принцип v1:
- PostgreSQL запускается в отдельном контейнере.
- Backend (NestJS) запускается в своём контейнере.
- Оба контейнера подключены к одной внутренней docker-сети.

Как строится связь:
1. Backend подключается к БД по внутреннему имени сервиса (например, `db`), а не по `localhost`.
2. Строка подключения хранится в env backend (`DATABASE_URL` или эквивалент).
3. Внешний доступ к БД из интернета не открывается (порт 5432 не публикуется наружу в prod).
4. Для сохранности данных используется docker volume для PostgreSQL.

Поток запуска:
1. Поднимается контейнер БД.
2. Поднимается backend и ждёт готовности БД.
3. Backend применяет миграции.
4. Backend начинает обслуживать API-запросы.

Что это даёт:
- Простая эксплуатация на одном сервере.
- Изоляция БД от внешнего доступа.
- Предсказуемый деплой и переносимость окружения.

## Open Question: стратегия refresh token

Нужно выбрать один из двух вариантов для v1.

### Вариант A: Refresh с хранением в БД (рекомендуется)

Суть:
- Access token короткоживущий JWT (stateless).
- Refresh token длинный.
- В БД хранится не сам refresh, а его хэш + метаданные сессии.

Плюсы:
- Нормальный `logout` и `logout all devices`.
- Можно отзывать украденные/подозрительные сессии.
- Поддерживает ротацию refresh и защиту от replay.

Минусы:
- Нужна таблица сессий и немного больше backend-логики.

### Вариант B: Refresh без хранения в БД (stateless refresh)

Суть:
- И access, и refresh валидируются только по подписи/сроку.
- Сервер не хранит refresh-сессии.

Плюсы:
- Проще реализация, меньше таблиц.

Минусы:
- Ограниченный revoke (почти нет точечного отзыва).
- Сложнее безопасно обрабатывать компрометацию refresh токена.
- Слабее контроль пользовательских сессий.

### Решение по умолчанию

Для этого проекта в прод-режиме предпочтителен **Вариант A**.
Вариант B допустим только как временный компромисс для максимально быстрого MVP.

## Open Question: хранение материалов через Google Drive + `file_url`

Возможный v1-вариант (бюджетный):
- Файл физически хранится в Google Drive.
- В БД хранится `file_url` (ссылка на файл), плюс метаданные материала.
- Backend управляет только бизнес-правами в системе (кто может видеть карточку/ссылку).

### Как это работает

1. Админ/преподаватель загружает файл в Google Drive (или вставляет готовую ссылку).
2. В `LessonMaterial` сохраняется:
- `title`, `description`, `file_type`
- `file_url` (google drive link)
- ACL-связи в `MaterialAccess`
3. Студент в UI видит материал только после проверки доступа в backend.
4. При открытии материала клиент переходит по `file_url`.

### Плюсы

- Быстрый старт без затрат на отдельное object storage.
- Минимум инфраструктуры на одном сервере.
- Простая ручная операционная модель для небольшой команды.

### Минусы и ограничения

- Управление доступом к самому файлу фактически на стороне Google Drive, не в нашем backend.
- Риск «битых» ссылок и ручных ошибок шаринга.
- Сложнее централизованный аудит скачиваний/просмотров.
- Переносимость ниже, чем у собственного storage-слоя.

### Правила для безопасного использования

- Хранить в БД только нормализованный `file_url` (валидировать домен/формат ссылки).
- Вести единые папки/структуру в Drive (по курсам/блокам).
- Запретить публичный broad sharing, где это возможно.
- Добавить периодическую проверку доступности ссылок (health-check job).

### Совместимость с будущей миграцией

Чтобы не застрять на Drive, в модели материалов предусмотреть:
- `storage_type`: `google_drive | local | s3`
- `file_url` для `google_drive`
- `storage_key` для `local/s3`

Так можно начать с Drive, а потом без ломки API перейти на local/S3-compatible storage.
