# Base44 и пакет `@base44/sdk`: обзор для проекта

## Что даёт платформа Base44

Base44 — это full-stack платформа для приложений, где в одном контуре находятся:
- модель данных (entities),
- API-слой к этим данным,
- функции/серверная логика,
- встроенные механики аутентификации,
- интеграции и деплой.

Для команды это обычно означает более быстрый старт: меньше ручной сборки инфраструктуры и меньше «клея» между фронтом, бэком и БД.

## Что даёт `@base44/sdk`

`@base44/sdk` — клиентский/серверный SDK для работы с Base44 API из кода.

В текущем проекте SDK используется как единая точка входа через `createClient(...)` в `src/api/base44Client.js`, после чего доступны доменные секции клиента:
- `base44.auth` — авторизация, профиль пользователя, login/logout,
- `base44.entities` — CRUD и выборки по сущностям,
- `base44.functions` — вызов serverless-функций,
- `base44.integrations` — вызовы подключённых интеграций (например, загрузка файлов),
- `base44.asServiceRole` (в serverless-функциях) — действия с повышенными правами.

## Что обычно есть «из коробки»

Типовой стек Base44 + SDK обычно включает:
- клиент инициализации по `appId`/token/base URL,
- доступ к сущностям через единый API (`list`, `filter`, `create`, `update`, `delete`, `bulkCreate` и т.д.),
- auth-поток (получение текущего пользователя, редиректы на login, logout),
- вызов функций (`functions.invoke(...)`),
- работу с файлами и внешними интеграциями,
- связь с GitHub/локальной разработкой (синхронизация кода и Builder).

## Как связаны БД, бэкенд и фронт

Упрощённая схема:
1. Фронт (React) вызывает `base44.entities.*`, `base44.auth.*`, `base44.functions.invoke(...)`.
2. SDK отправляет запросы в backend Base44 по `appBaseUrl`/`appId`.
3. Backend Base44 работает с данными приложения (entities) и применяет политики доступа.
4. Для сложной логики вызываются функции в `base44/functions/*`.
5. Внутри функций можно использовать `createClientFromRequest` и `asServiceRole` для защищённых операций и сценариев, где нужны сервисные права.

## Плюсы использования

- Высокая скорость разработки: меньше инфраструктурного кода.
- Единая модель данных и API: проще поддерживать консистентность.
- Удобный DX для фронта: один SDK для auth/entities/functions.
- Быстрый деплой и синхронизация с Base44 Builder.
- Хорошо подходит для CRUD-heavy систем и внутренних продуктов.

## Минусы и ограничения

- Vendor lock-in: архитектура и API сильно привязаны к Base44.
- Ограничения кастомизации: не все low-level сценарии так гибки, как в self-hosted backend.
- Зависимость от облачной платформы и её SLA/изменений.
- При росте нагрузки/сложности может понадобиться вынос части логики в отдельные сервисы.
- Миграция на другой backend в будущем может быть трудозатратной.

## Когда подход оправдан

Base44 + `@base44/sdk` рационален, если приоритет — быстрое развитие продукта и небольшая стоимость изменений на ранних этапах. Для сценариев с жёсткими требованиями к полной инфраструктурной независимости или глубокой кастомизации backend-слоя нужно заранее закладывать стратегию выхода/гибридную архитектуру.
