# GAP-анализ: ТЗ vs текущая реализация

База сравнения:
- TO-BE: `docs/tz-technical-structured.md`
- AS-IS: `docs/as-is-system-spec.md`
- Потоки/данные: `docs/as-is-data-and-flows.md`

Шкала приоритета:
- `P0` критично для корректности бизнеса/денег
- `P1` важно для выполнения ТЗ и стабильности процессов
- `P2` улучшение/доведение до целевого UX

## P0 (критично)

### 1) Биллинг: ручные начисления
- Область: Баланс и оплаты
- Требование ТЗ: Начисления только через платёжный контур, ручные начисления запрещены.
- Текущее состояние: В `Payments` доступны ручные create/edit/delete с прямой правкой `lesson_balance`.
- GAP: Прямой конфликт с ТЗ, риск финансовых ошибок.
- Что делать: Закрыть ручные начисления, оставить controlled-операции через backend-функции.

### 2) Единая точка истины баланса
- Область: Баланс и оплаты
- Требование ТЗ: Детерминированное списание/начисление по единым правилам.
- Текущее состояние: Баланс меняется в нескольких местах (UI + serverless).
- GAP: Риск двойного списания и рассинхронизации.
- Что делать: Централизовать операции баланса в server-side функциях, UI только вызывает команды.

### 3) Telegram security
- Область: Интеграции / безопасность
- Требование ТЗ: Критичные действия через систему.
- Текущее состояние: Есть прямые client-side вызовы Telegram API в админ-экране.
- GAP: Риск компрометации токена и неаудируемые отправки.
- Что делать: Убрать прямые клиентские вызовы, все отправки только через serverless.

## P1 (важно)

### 4) Несогласованные статусы урока
- Область: Расписание и уроки
- Требование ТЗ: Канонический статус `missed_without_notice`.
- Текущее состояние: Используется `missed_no_notice`.
- GAP: Несогласованный словарь статусов.
- Что делать: Ввести единый enum, сделать миграцию данных и рефактор проверок.

### 5) Ограничение на `missed_without_notice`
- Область: Расписание и уроки
- Требование ТЗ: Нельзя выставлять до фактического окончания урока.
- Текущее состояние: Явного server-side запрета не найдено.
- GAP: Возможны некорректные статусы.
- Что делать: Добавить backend-валидацию при update статуса.

### 6) Отмена учеником по правилу 2 часов
- Область: UX уроков
- Требование ТЗ: `>=2ч` без списания, `<2ч` со списанием; кнопка скрывается после действия.
- Текущее состояние: Полноценный поток отмены учеником не найден.
- GAP: Функциональный пробел.
- Что делать: Реализовать server-side команду отмены + UI-кнопку + аудит.

### 7) Серии уроков: удаление
- Область: Расписание и уроки
- Требование ТЗ: Удаление одного / всех последующих / всей серии.
- Текущее состояние: Есть создание серии, но нет режимов удаления.
- GAP: Неполный recurring-flow.
- Что делать: Добавить операции по `recurring_group_id` с 3 режимами.

### 8) Онлайн-оплата: модель статусов
- Область: Баланс и оплаты
- Требование ТЗ: Чёткая модель `pending -> success`.
- Текущее состояние: Логика есть, но часть данных хранится в `comment`.
- GAP: Технический долг модели `Payment`.
- Что делать: Нормализовать поля (`payment_status`, `gateway_order_id`, `source`, `processed_at`).

### 9) Контроль критичных операций
- Область: Ограничения и безопасность
- Требование ТЗ: Критичные действия только через систему.
- Текущее состояние: Часть критичной логики реализована на фронте.
- GAP: Недостаточная жёсткость контроля.
- Что делать: Вынести правила в policy-layer на backend, добавить idempotency.

### 10) Модуль тестирования (LMS tests)
- Область: Тестирование
- Требование ТЗ: Полный контур `Test -> Blocks -> Variants -> Groups -> Questions`.
- Текущее состояние: Модуль отсутствует.
- GAP: Крупный функциональный пробел.
- Что делать: Выделить отдельный этап реализации с отдельной спецификацией.

## P2 (улучшения)

### 11) Отмена преподавателем: формализация
- Область: UX уроков
- Требование ТЗ: Уведомление ученика при отмене.
- Текущее состояние: Отмена есть, но без единого обязательного backend-пайплайна.
- GAP: Неполная формализация процесса.
- Что делать: Централизовать через серверную функцию с обязательным notify.

### 12) Календарные ограничения (выходные/праздники)
- Область: Расписание
- Требование ТЗ: Настройки запрета назначения на выходные/праздники.
- Текущее состояние: Не найдено.
- GAP: Отсутствует бизнес-ограничение.
- Что делать: Добавить календарь и проверки при создании/изменении уроков.

### 13) Telegram: отложенные и сегментные рассылки как процесс
- Область: Telegram
- Требование ТЗ: Рассылки сегментам и отложенные сообщения.
- Текущее состояние: Базовые уведомления есть, процесс частично ручной.
- GAP: Неполное покрытие коммуникаций.
- Что делать: Ввести очередь сообщений, шаблоны, журнал отправок.

### 14) Группы как отдельный модуль
- Область: Группы
- Требование ТЗ: Создание групп, назначение учеников, групповая логика.
- Текущее состояние: Есть `student_ids` в уроках, отдельного модуля групп нет.
- GAP: Частичное соответствие.
- Что делать: Добавить `Group` + membership + связь с расписанием.

### 15) Миграция расписания из Excel
- Область: Миграция
- Требование ТЗ: Перенос из Excel.
- Текущее состояние: Не найдено.
- GAP: Пробел миграционного контура.
- Что делать: Реализовать импортёр CSV/XLSX с dry-run и валидацией.

### 16) Нефункциональные KPI
- Область: Производительность
- Требование ТЗ: Высокая скорость работы.
- Текущее состояние: Формальных SLA/perf-метрик нет.
- GAP: Нет измеримой цели по производительности.
- Что делать: Зафиксировать KPI (TTI, API latency), добавить мониторинг.

---

## Рекомендуемый порядок закрытия

1. `P0`: биллинг/баланс и Telegram security.
2. `P1`: статусы, отмены, recurring-delete, модуль тестирования.
3. `P2`: календарь, группы, миграция, эксплуатационные улучшения.

## Минимальный DoD следующего релиза

- Нет ручных начислений баланса из UI.
- Все изменения баланса выполняются через server-side функции с журналированием.
- Единый enum статусов урока без legacy-вариантов.
- Работает сценарий отмены учеником с правилом `2 часа`.
- Telegram отправка выполняется только server-side.
